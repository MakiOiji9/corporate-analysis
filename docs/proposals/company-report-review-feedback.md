# 提案: 企業分析レポートのレビュー指摘への対応

対象レポート `companies/3798_uls-group/reports/2026-11-22_company-report.html`（判定規則の版 2）について、外部レビューから「分析内容」と「読みやすさ」の2つの観点で指摘を受けた。この文書では、各指摘をレポートとコードで確かめた結果（原因の箇所）と改善案をまとめる。実装の前にレビューを受けるための提案書で、**「8. 確認したいこと」に挙げた方針が決まるまでは実装しない**。

## 1. 目的

- 章をまたいで判定・数字が食い違わないようにする。今はレポートの信頼を下げる一番の原因になっている。
- 結論が「根拠の弱い加点」や「甘い悲観シナリオ」に頼っていないかを、読み手が確かめられるようにする。
- 分量と重複を減らし、「結論 → 根拠 → 結論が変わる条件」を短い時間で読めるようにする。
- 修正はスクリプトの側で行い、ほかの企業のレポートにも同じ形で効くようにする（このリポジトリの方針どおり、判定と HTML は Python が出す）。

## 2. 指摘の確認結果（原因の特定）

各指摘をレポート本文とコードで確かめた。「区分」は次の3つ。

- **バグ**: 実装の誤りで、直せば済むもの

- **表示**: 計算は正しいが、見せ方のせいで誤解を生むもの

## 3. 改善の方針

1. **1つの概念は1か所で計算し、どの章もそこから引く**（A2・A3・A4・A12）。章ごとに選び直したり言い換えたりしない。
2. **章をまたいだ食い違いを build のときに機械で検出する**（新しいチェック）。直しても、別の会社や別の版で同じことが起きるため。
3. **結論の頑健さを見せる**（A1・A5・A7）。点数をそのまま出すだけでなく、「弱い根拠を外しても判定は同じか」を併記する。
4. **読み手の言葉に統一する**（B2〜B7）。内部用語と注意書きの繰り返しは、文言のチェックで出さないようにする。
5. **章の構成は「結論 → 結論が変わる条件 → 根拠 → 付録」の順にする**（B1・B8）。

## 4. 改善案（分析内容）

### P0（食い違い・バグ。方針の確認なしで直せるもの）

#### 4.1 モートの言葉の取り違え（A2）
- `cr_judge.mover_text()` で、点数から判定の言葉を逆算しない。要素の行が持っている**判定の言葉そのもの**（`row["value"]` の「なし」）を「今は」の側に使う。
- モートの点数の段は −1（なし・超過収益なし）／0（なし・超過収益あり）／+0.5（狭い）／+1（広い）で、ほかの要素の3段と違う。動いた先の言葉もこの段で書く。
  - 下がる向き: 今の文「モートが「なし」になれば（今は「狭い」）」→「超過収益（資本コストを上回る利益）が無くなれば（今はモート なし・超過収益あり）」
  - 上がる向き: `_next_word` は 0 → +1（広い）と動かすが、1段上は「狭い」（+0.5）なので、モート専用の段に合わせる。
- テスト: 「なし（超過収益あり）」のときに「狭い」が出ないこと。

#### 4.2 短期の価格の目安を1か所にまとめる（A3）
- 支持線・抵抗線の**役割を読み替える処理（`_role`）を `cr_technicals.levels()` に移し**、`resistances` に「以前の安値（今は上値の抵抗）」も含めた1本の一覧にする。03章（`cr_scenarios`）と07章はどちらもこの一覧を使う。
- 488円（以前の安値）と 549円（直近の高値）のどちらを先に置くかは、「近い順」に統一する（今の 03章と同じ）。
- テスト: 03章の利益確定1・2と07章の利益確定の目安が同じ価格になること。

#### 4.3 ATR の単位（A10）・在庫の文言（A11）・分割の表示（A8）
- ATR: `cr_tech_views` の文言を足の種類で切り替える（日足「1日あたり」、週足「1週あたり」）。
- 在庫: `cf_metrics` の注記を、増加率が売上を上回った項目ごとに出し分ける（売上債権→「回収できていない売上の可能性」、棚卸資産→「売れていない在庫の可能性」）。
- 分割: `cr_sections` で、`kind` が株式分割のときは増加率でなく倍率を出す（「2014-03 株式分割（約101倍。1:100 の分割と推定）」）。分割の比率で説明できない増加分（2026-03 の約 157 万株）があるときは「分割のほかに約 157 万株の増加（内訳は有報で要確認）」と分ける。比率の読み取りは `tools/analysis/gr_facts.py` が `株式分割（1:10）` の形を読んでいるので、それを使えるか確かめる。

#### 4.4 中期の基本ケースの説明（A12）
- 「各指標の中心（適正）」をやめ、何の値かを出す: 「3つの指標の帯の中央の中央値（PER 893・PBR 736・PEG 750 → 750）」。
- PEG の帯の中央（PEG 1.5倍）は「適正」と呼べないため、PEG の中央は **PEG 1倍の株価**（帯の下限）にするかどうかを「8. 確認したいこと」Q5 で確かめる。

### P1（規則の見直し。方針の確認が要るもの）

#### 4.5 半点の加点の見直しと頑健さの表示（A1）
次の2つを組み合わせる案。どれを採るかは Q1 で確かめる。

- **(a) しきい値ちょうどは動かさない**: `abs(lean) >= LEAN` を `>` にする。policy.md 6「迷う場合は低い方」に合う。今回の成長性は +0.25 ちょうどなので 0 点になり、中期・長期はウォッチになる。
- **(b) 懸念の内訳があるときは上に動かさない**: 内訳に −1（「問題あり」など）が1つでもあれば、「普通」を +0.5 に上げない。
- **(c) 頑健さを表示する（どちらの案でも入れる）**: 半点の加点・減点を 0 に戻したときの判定を計算し、判定が変わるときは期間のカードに「この判定は ○○ の半点の加点に頼っている（外すとウォッチ）」と出す。`cr_judge.sensitivity()` に1つ計算を足すだけで済む。

(a)・(b) は判定規則が変わるため、判定規則の版を 3 に上げる（過去のレポートは作成時の版で判定したまま。BL-27 の仕組み）。

#### 4.6 悲観シナリオに減益のケースを入れる（A5）
今の「基本の半分」は、最大の脅威（人月モデルの崩壊）を反映しない。次のどちらかにする（Q2）。

- **(a) 過去の実績で下限を決める**: 悲観 ＝ min(基本の半分, 過去10年で最も悪かった EPS の年の伸び率)。データがあり、機械的に決められる。3798 では過去の減益年（成長性分析の `declines`）の値を使う。
- **(b) SWOT の最大の脅威が「大」のときは減益ケースを足す**: 「EPS が 3年で −X%」の4つ目のケースを足す。X をどう決めるか（固定値か、過去の最悪の年か）が要る。

どちらでも、長期の売りの目安「EPS の伸びが悲観ケースを下回り続けたら見直す」は残す。悲観がマイナスになったときの文言（「減り方が悲観ケースより大きければ」）も用意する。

#### 4.7 リスクリワード 1 未満の扱い（A7）
- 1 未満の候補の行に「利益確定までの上げ幅より損切りまでの下げ幅が大きい」と注記し、色を変える。
- 候補から外すか、注記だけにするかは Q3 で確かめる。全候補が 1 未満のときは「チャートの上では今は買いの条件が良くない」と1行で結ぶ。

#### 4.8 テクニカルの時間軸をそろえる（A4）
- 点数（`cr_technicals`、週足）と08章の総合（`cr_tech_views`、日足と週足）のどちらを正にするかを決める（Q4）。案は「点数は今のまま週足、07章・08章では**点数に使った週足の結論を先頭に出し**、日足の結論は『短い流れ』として並べる」。名前も「株価のテクニカル（週足）」と書く。
- 08章のトレンドの確度: 根拠の行のうち、そろっていない行（「並びがそろわない」「ダウ理論: そろわない」）がある場合は「高」にしない。`cr_tech_views` の確度の数え方を見直す。

#### 4.9 β の信頼性の表示（A9）
- `cr_moves.beta()` で相関（または決定係数 R²）も出し、R² が低い（案: 0.1 未満）ときは「市場の動きで説明できる分」の分解を出さず、「日経平均との連動がほとんどない（相関 0.02）。市場で説明できる分は求められない」と書く。
- 比べる指数は日経平均だけで、小型株には合わないことが多い。`market/data/japan_series.csv` にある業種の指数（TOPIX-17 の業種 ETF、`JP_SEC_16xx`）で計算するかどうかは Q6 で確かめる（TOPIX は集めていない）。

#### 4.10 出典の記録（A6）
- BL-01（証拠の連鎖）を STEP 1 の4分析に広げる。3798 は次に STEP 1 を作り直すとき（365日有効）まで直らないため、それまでは 04章の「未検証（出典の記録なし）」を各行に出さず、**節の頭に1回**「この節の評価は出典の記録が無く、判定の確度を下げて読む」と出す（読みやすさの B7 と同じ考え方）。

## 5. 改善案（読みやすさ）

### P0（文言のバグ）

#### 5.1 「判定を動かす要因」の文（B2・B3・B4）
- 「最も近い境目」と「投資検討まで／見送りまで」を重ねて出さない。期間ごとに**1文**にする。
  - 例: 「投資検討の境目（+0.25）まで、あと 0.20 点上がれば届く。見送りの境目（−0.25）までは 0.30 点の余裕がある。」
  - 例（今が投資検討）: 「投資検討の境目（+0.25）を 0.03 点上回っているだけで、境目に近い。」
- 符号は使わず「上がれば／下がれば」「上回る／余裕がある」で向きを書く。「点」は数字の直後に置く。
- 半点の要素の動きは「成長性の内訳の寄りが無くなれば（今は「普通」を +0.5 点で数えている）」のように、何が変わるかを書く。

#### 5.2 内部用語のチェック（B6）
- build の最後に、HTML の本文から**使ってはいけない言葉**を探すチェックを足す（`tools/report/sanity.py` か新しい `cr_lint.py`）。見つけたら build を失敗させるか、警告にするか（Q7）。
  - 対象の案: `raw`・`スクリプト`・`判定候補`・`json`・`版1`/`版2`・`FILL`・`brief`
- 置き換え: `sw_brief.STATUS_LABEL` の「raw に無い」→「集めた資料に無い」、`ff_inputs` も同じ。分析の LLM の本文に「スクリプトの判定候補」と書かせないよう、各スキルの文章の指示に一文足す。
